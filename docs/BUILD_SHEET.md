Claude build sheet: Milestone 1 browser-agent demo

Instruction to Claude

Build a working, reviewable concept demo for a healthcare revenue-cycle company’s paid-trial scope. Implement the project, run meaningful tests, and provide startup instructions and a short architecture note. This is an independently built portfolio demo using synthetic data, not a client deployment or proof of HIPAA compliance. Do not claim completion without runnable evidence. Work sequentially unless the user authorizes parallel agents.

Read any repository instructions first. Inspect existing code before choosing whether to extend it or create a new project. Use synthetic data exclusively. Never access real patient records, EMR systems or payer portals.

1. Product requirements

Client’s exact Milestone 1 deliverable

Chrome side-panel extension with chat; agent navigates a provided synthetic test site, finds a record, and returns a structured result with source URL and time. Allowlist of permitted sites. Short architecture note.

The full specification applies data-handling and provider restrictions across milestones. Include baseline enforcement now; do not defer it merely because dedicated policy/security milestones come later.

Demo user journey

1. Operator opens a dedicated Chrome profile and the installed extension.
2. Operator opens the side panel and enters a task such as finding synthetic record SYN-1042 and reporting its claim status and balance.
3. Agent uses a small set of browser tools to navigate the allowlisted synthetic site and inspect DOM data.
4. The panel shows content-free progress messages, then a structured result containing the synthetic record identifier, requested fields, source URL and retrieval timestamp.
5. Audit view shows action type, policy outcome, task/action IDs and time, with no page text, record values, screenshots or prompt content.
6. An attempted write, off-allowlist destination or authentication interaction is blocked or paused with a clear explanation.

Scope boundaries

Include: extension chat, real Playwright-controlled Chrome, synthetic site, one real approved model provider, provider abstraction, constrained tools, allowlist, basic read-only policy, result display, metadata audit, tests and architecture note.

Defer: production EMR/payer adapters, Postgres persistence, trace-viewer containers, Azure deployment/IaC, scheduled jobs, file downloads, screenshot/vision support, persistent crash recovery, mid-task redirect, full resume, write approvals and production authentication. These belong to later milestones. Show unsupported capabilities explicitly rather than simulating completion.

Chat is text task input plus progress/results, not unrestricted conversational memory. Keep demo state in memory; do not put task/result content into browser storage or local files.

2. Engineering specification

Proposed implementation

Use TypeScript throughout unless the existing repository strongly favors Python. Components:

• Chrome Manifest V3 extension: side panel UI and narrowly scoped permissions.
• Local backend: task coordinator, model adapter, policy engine, Playwright bridge and metadata event store.
• Synthetic site: deterministic fake records, search/detail pages and deliberate prohibited controls.
• Tests: unit policy checks and integration tests against the synthetic site; a real-provider smoke test separate from deterministic mocked-provider tests.

This prototype uses an operator’s local dedicated Chrome controlled through Playwright over a loopback-only CDP endpoint. It is not a cloud backend controlling a user’s browser remotely. Document the distinction and the later production design decisions.

Browser bootstrap

Use a dedicated, non-default Chrome profile, never the operator’s normal profile. Bind remote debugging and backend services to loopback only. Provide an explicit launch command/script for supported OSes and a manual fallback, verify the connection, and refuse unrelated profiles/tabs. Do not reuse signed-in production sessions.

Where local Chrome support differs by OS/version, report the supported/tested setup instead of assuming universal compatibility. Do not expose a CDP port publicly. Only control the dedicated task tab.

Extension/backend connection

Use a session-scoped secret generated by the backend and entered by the operator. Do not hard-code a universal token or bake provider credentials into the extension. Verify authentication and permitted extension origins for HTTP/WebSocket connections. Use strict origin/CORS checks; require JSON/custom authentication headers for mutating endpoints. Do not allow arbitrary websites to start tasks against the local backend. Redact connection/auth errors.

Model interface

Define a provider interface for planning and constrained tool requests. For this independent demo, enable one approved Anthropic or OpenAI API endpoint/model through environment configuration and supply a second adapter stub if necessary. The client’s later Milestone 2 requires both providers to work by configuration; do not claim that requirement has passed with only one adapter.

Approved provider/model/endpoint configuration must be explicit. Reject unapproved choices before a request is sent. Never accept a user-supplied arbitrary endpoint. Keys stay backend-only in environment configuration for the local demo; document that production requires the client’s secrets store and healthcare agreements. Never request keys in chat or include them in code, logs, traces or screenshots.

Do not use Anthropic’s separate browser-use toolset. This demo uses your own constrained DOM tools. Do not use screenshots in Milestone 1; fail clearly on unsupported scanned/image content.

Bound task steps, extracted data size, model calls, retries and execution time. Track available token usage and estimated cost per task using configurable rates; label estimates as estimates. Abort loops. A deterministic fake provider may power tests, but the runnable demo must offer real model execution and identify its mode visibly.

Constrained tool contract

Expose only typed tools with schema validation. Suggested tools:

• navigate: approved synthetic route only.
• inspect: bounded, filtered DOM/text for the synthetic application’s approved regions.
• lookup_record: permitted search interaction with validated synthetic record identifier.
• open_record: validated approved record-link identifier.
• finish: structured result with source evidence.

Avoid generic arbitrary JavaScript evaluation, shell access, unrestricted click/type tools, arbitrary selectors or raw Playwright access from the model. Resolve validated tool identifiers server-side. Never let page text grant permissions or change policy.

Allowlist and read-only enforcement

Use exact scheme/hostname/port checks and approved routes; reject deceptive subdomains, userinfo, unsupported schemes and malformed URLs. Validate navigations, redirects, popups and subresource requests. Explicitly allow the synthetic site and configured model endpoint; block other outbound hosts, disable model SDK telemetry, and use a network test to verify runtime behavior. Note that browser background traffic needs separate treatment; application interception alone is not system-wide network containment.

For the synthetic site, allow only known read routes and interaction handlers. Classify actions before execution. Block save/send/submit/delete/update controls, form mutations and mutating network requests. Do not treat GET as universally harmless or POST as universally a write: use route semantics for this controlled site. Search may be permitted only when confirmed to be read-only.

Add synthetic server mutation counters so tests prove record state did not change. Enforce policy below the model: a model saying an action is safe is not authorization. Do not claim the controlled-site policy makes arbitrary third-party portals safely read-only; site-specific adapters and stronger network boundaries are future work.

Authentication boundaries

Never extract, type, store or send passwords, tokens, cookies, browser storage or MFA codes to the model. Detect authentication pages/forms before DOM extraction and pause with human_action_required status. Do not capture whole-page DOM that includes credential fields or hidden secrets. Include a synthetic login challenge fixture. For Milestone 1, stop/pause cleanly; full post-login resume is later scope.

Data handling

Use fake records labeled SYNTHETIC—NOT REAL PATIENT DATA. Content may exist in transient process memory and the side-panel result display. Do not persist it outside the future client-controlled Postgres results store. Milestone 1 has no persistence.

Audit/log records: generated task/action IDs, action category, outcome, timestamp, duration and safe error code only. Do not log prompts, DOM, extracted fields, model payloads, screenshots or raw stack/error objects that contain content. Source URL belongs in the displayed result, not audit events; synthetic URLs must not contain patient names or sensitive values.

Disable analytics, SDK tracing, crash reporting and telemetry. Check defaults. Disable Playwright traces, screenshots, videos and content-bearing test attachments. Use unique synthetic leak markers to scan captured logs and CI artifacts without printing the markers or matching content on failure. Dependency installation traffic is separate from the runtime traffic test.

Dedicated Chrome can create cache/history/profile artifacts. Minimize persistence, disable downloads and use an isolated disposable profile; inspect residual artifacts. Do not claim strict no-local-copy compliance unless verified. If Chrome persistence prevents satisfying it, document the gap and required production containment rather than silently ignoring it.

Result schema and factual checks

Task result includes task_id, status, record_id, requested_fields, source_url and retrieved_at in UTC ISO 8601. For unsupported/ambiguous data, return uncertain/not_found instead of guessing.

Populate source_url and retrieval time from the browser/coordinator, not model invention. Validate returned fields against the extracted record evidence. Do not assign numerical confidence without calibration. If evidence conflicts, display uncertainty. Store no content-bearing evidence in audit logs.

3. Interface/design requirements

Professional, compact side panel with task input, Run button, progress state and result card/table. Show provider/mode and synthetic-only badge. Support idle/running/success/not_found/blocked/human_action_required/error states. Prevent duplicate task starts while one is active. Include a clear stop control that halts execution; full resume is out of scope.

Display safe errors with suggested next action. Make source links explicit and timestamp readable. Keep audit metadata in a separate expandable section. Do not place API keys in UI or marketing claims about compliance. Aim for readable keyboard-accessible controls and clear loading states.

4. Verification and acceptance

Automate meaningful checks, not tests that simply restate implementation. Required cases:

|Test                      |Pass criteria                                                                                                     |
|--------------------------|------------------------------------------------------------------------------------------------------------------|
|Happy path                |Real browser navigates synthetic site and returns exact expected record fields with actual source URL and UTC time|
|Unknown record            |not_found; no invented fields                                                                                     |
|Ambiguous/conflicting data|uncertainty returned or task rejected; no unsupported certainty                                                   |
|Invalid tool arguments    |Rejected before browser execution                                                                                 |
|Write attempt             |Blocked and metadata event recorded; server mutation counter unchanged                                            |
|Off-site URL              |Blocked before navigation, including redirect and popup cases                                                     |
|Credential fixture        |Pauses before extracting/typewriting sensitive fields; no auth material reaches model                             |
|Prompt injection fixture  |Synthetic page instructions cannot override policy or produce prohibited tool execution                           |
|Leak markers              |No synthetic markers in logs, traces, errors, CI artifacts or persistent application storage                      |
|Unapproved provider       |No network call; safe rejection event                                                                             |
|Provider outage           |Safe error, bounded retries and no payload leakage                                                                |
|Backend authentication    |Unauthenticated/unapproved-origin task requests rejected                                                          |
|Stop/step budget          |Active task terminates without further browser/model actions                                                      |
|Runtime network           |Application sends only approved traffic; distinguish any uncontained Chrome background traffic                    |

Tests may deliberately use synthetic prompt-injection fixtures to evaluate this user-owned demo. Keep fixtures local and synthetic.

Choose a small declared test suite (for example 10 deterministic tasks) and report the actual numerator/denominator. Run at least one explicitly labeled real-provider end-to-end smoke test when a key is available. If no key is configured, complete deterministic tests and report the real-provider test as pending; do not fake it.
